# Integration instructions

## Baseline

* Repository: `jelincovil/tws-palomar`, fixed commit `1121b6d5d00ab04be218fea36a4eb36d5990f287`.
* The baseline files were supplied as attachments and read directly: `Solution.lean`,
  `lean-toolchain`, `lakefile.toml`, `lake-manifest.json` and `CASCADE_THEOREM.md`. GitHub was
  not contacted.
* None of these files was modified. `git diff` against the initial project commit is empty
  for all of them; SHA-256 values are listed in `VERIFICATION.txt`.
* `Challenge.lean` is not imported, and it is not present in this project.

## File layout

The extension is a separate Lake package in a subdirectory of the baseline checkout:

```
<baseline checkout>/                  (unchanged baseline: Solution.lean, lakefile.toml, ...)
└── extension/
    ├── lakefile.toml                 (extension package configuration — new)
    ├── ThresholdExtension/
    │   ├── ThresholdCertificate.lean     (abstract module, imports only Mathlib)
    │   └── Db2ThresholdCertificate.lean  (bridge; imports the abstract module and `Solution`)
    ├── THRESHOLD_CERTIFICATE_SPEC.md
    ├── INTEGRATION.md
    └── VERIFICATION.txt
```

Two further files live in `extension/` in this project but are not part of the review
package:

* `lake-manifest.json` is generated by Lake on the first build.
* `AxiomCheck.lean` holds the `#print axioms` commands. Its full contents are reproduced in
  `VERIFICATION.txt`.

## Import paths

* `ThresholdExtension.ThresholdCertificate` contains `public import Mathlib`.
* `ThresholdExtension.Db2ThresholdCertificate` contains
  `public import ThresholdExtension.ThresholdCertificate` and `public import Solution`.
  `Solution` is the real baseline module. It resolves through the path dependency on the
  parent package `tws-palomar`, so the bridge is checked against the actual baseline proofs of
  `TWSPeriodic.cascade_opNorm_uniform` and `TWSPeriodic.cascade_opNorm_formula`.

Both files start with `module` and use `@[expose] public section`, matching the baseline's style.

## Added configuration: `extension/lakefile.toml`

```toml
name = "tws-threshold-extension"
version = "0.1.0"
defaultTargets = ["ThresholdExtension"]
packagesDir = "../.lake/packages"

[leanOptions]
autoImplicit = false
relaxedAutoImplicit = false

[[require]]
name = "mathlib"
git = "https://github.com/leanprover-community/mathlib4.git"
rev = "065356127b1dc0016f66b7283ce0ce2c4055aa55"

[[require]]
name = "tws-palomar"
path = ".."

[[lean_lib]]
name = "ThresholdExtension"
roots = ["ThresholdExtension.ThresholdCertificate", "ThresholdExtension.Db2ThresholdCertificate"]
```

What each part does:

* **Mathlib pin.** The extension pins the same Mathlib revision as the baseline `lakefile.toml`.
  The generated `extension/lake-manifest.json` resolved every transitive dependency to the
  same revision as the baseline `lake-manifest.json`; this was checked.
* **`packagesDir = "../.lake/packages"`.** The extension reuses the baseline's dependency
  checkout instead of cloning Mathlib a second time.
* **`tws-palomar` path dependency.** The parent package is used exactly as it is. Its own
  configuration and manifest are read but not edited.

### Toolchain file

* The extension has no `lean-toolchain` of its own, so elan resolves the parent's file.
* On its first build, Lake auto-wrote `extension/lean-toolchain` containing
  `leanprover/lean4:v4.35.0-rc2`, copied from Mathlib's own toolchain at the pinned
  revision. I deleted it. It is not part of the package.

See `VERIFICATION.txt` for the toolchain discrepancy.

## Reused baseline declarations (all in namespace `TWSPeriodic`, from `Solution.lean`)

| Declaration | How it is used |
|---|---|
| `cascadeOperator` | the operator `T := cascadeOperator j N 1` |
| `cascadeSupport` | the hypothesis `cascadeSupport j ≤ N` for the exact level |
| `cascade_opNorm_uniform` | gives `‖cascadeOperator j N 1‖ ≤ 1651/1395` |
| `cascade_opNorm_formula` | gives `‖cascadeOperator j N 1‖ = c_j` |

Nothing is reproved, restated as an axiom, or replaced by a hypothesis.

## Reproducing the build locally

1. Check out the baseline at commit `1121b6d5…` and obtain its dependencies as usual. From the
   baseline root, run `lake exe cache get`, then `lake build Solution`.
2. Copy the `extension/` directory, with `lakefile.toml` and the two `.lean` files under
   `ThresholdExtension/`, into the baseline root.
3. In `extension/`, run `lake build`. This builds both extension modules. It also needs the
   `Solution` olean, which Lake builds or replays from step 1.
4. For the axiom audit, create `extension/AxiomCheck.lean` with the contents given in
   `VERIFICATION.txt`, then run `lake env lean AxiomCheck.lean` from `extension/`.

### Caveats

* **Toolchain.** The checks reported here were run with Lean `v4.35.0-rc2`. This is the
  toolchain that Mathlib's own `lean-toolchain` declares at the pinned revision. The
  baseline's `lean-toolchain` says `v4.28.0`, which was not available here.
  * If your environment really uses `v4.28.0` with this Mathlib revision, the build is
    untested there.
  * On older Mathlib, the one name that may need reverting is `Set.mem_ofPred_eq`, back to
    `Set.mem_setOf_eq`.
* **Default target.** Running plain `lake build` in the baseline root tries the default target
  `Challenge`, whose source file was not supplied. Build `Solution` explicitly instead.
